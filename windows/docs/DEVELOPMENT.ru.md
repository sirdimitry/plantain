# Разработка Windows

## Размещение и ветки

Рабочая копия: D:\Projects\plantaine. Репозиторий: https://github.com/sirdimitry/plantain. Ветка macOS — main; параллельная ветка Windows — windows. В main допустимо обновлять README о наличии Windows; Swift-код, macOS-скрипты, тесты и корневой VERSION при этом не меняются.

Материалы Windows находятся внутри windows/. Будущие исходники — windows/src/, тесты — windows/tests/, скрипты — windows/scripts/, результаты локальной сборки — windows/artifacts/. Эти каталоги появятся по мере реализации; сейчас C#-проекта нет. Не переносить файлы разработки за пределы D:\Projects\plantaine.

## Последовательность

1. Требования и матрица приёмки — завершено в 0.1.0-dev.1.
2. Независимый движок C# и автоматические тесты: модели API, пагинация, проверки файлов, потоковая передача, повторы, отмена, политика сети. Подготовить необходимый .NET SDK, не добавляя его в пользовательские требования.
3. Файловая безопасность Windows: имена, коллизии, reparse points, блокировка назначения, публикация без замены, внешние и сетевые тома.
4. WPF-интерфейс и интеграция: события прогресса, системные папки и диалоги, Проводник, завершение работы, управление сном, доступность и масштабирование.
5. Реальная Windows и portable-сборка с включённой средой .NET; результаты приёмки, контрольные суммы и обновлённая документация.
6. Установщик — позже, вне текущего этапа. ARM64 и автообновление также требуют отдельного объёма работ.

## Правила версий и коммитов

- Корневой VERSION относится только к macOS. windows/VERSION — единственный источник номера Windows. Пока нет исполняемого приложения, номер обозначает версию материалов разработки, что обязательно написано в README.
- Текущая исходная точка Windows — 0.1.0-dev.1. Следующий завершённый шаг разработки повышает dev.N; изменение возможностей повышает minor по мере зрелости проекта, совместимое исправление стабильной версии — patch, несовместимое изменение — major. До стабильного выпуска сохраняется предварительный суффикс. 1.0.0 означает выполненную приёмку, а не просто успешную компиляцию.
- Документационные исправления сами по себе не повышают номер приложения. Не повышать версию macOS из-за работы Windows. Не создавать тег и GitHub Release для документационного этапа.
- В каждом содержательном коммите обновлять CHANGELOG и затронутый README по фактическим изменениям. Оба README проверять на актуальность; перекрёстные ссылки и сведения о стадии должны совпадать. Не менять текст второго README ради формального изменения файла.
- В README/CHANGELOG явно различать «описано», «реализовано», «собрано», «проверено автоматически», «проверено на реальной Windows». Провал проверки не считается завершённым этапом и не скрывается повышением версии.
- Результаты проверок относятся к проверенному коммиту/состоянию дерева; хеш коммита берётся из Git, а не встраивается в тот же коммит с самоссылкой. Для будущих сборок номер брать из windows/VERSION, идентификатор сборки — из Git; при локальных изменениях добавлять пометку dirty. Автоматизацию подключить вместе с проектом, сейчас это политика, а не готовый механизм.
- Перед публикацией проверить diff и отсутствие изменений Sources/, Tests/, scripts/, Assets/, docs/ macOS и корневого VERSION. Затем коммит и push в windows. После изменения README в main синхронизировать его в windows без обратного слияния Windows-кода в main.

## Технические ориентиры

Выбран C# / .NET 10 LTS и WPF; первая целевая система — Windows 11 x64. Движок не должен зависеть от WPF. Интерфейсы API, файловой публикации, часов/повторов и отчёта о прогрессе должны допускать независимые проверки. Без установщика и обязательной предварительной установки .NET у конечного пользователя.

Официальные справочные материалы: [WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/), [жизненный цикл .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core), [упаковка приложения](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview), [имена файлов Windows](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file). Они дополняют контракт, но не заменяют проверку реальной реализации.
